# 外贸获客智能体 Demo - 产品需求文档

## Overview
- **Summary**: 一个 PDF 驱动的外贸获客智能体 Demo，用于验证系统是否能够基于任意公司导航/产品资料 PDF，自动完成公司画像识别、候选客户获取、客户分级、动作建议、飞书落地及流程可视化展示。
- **Purpose**: 解决外贸销售场景中的两个典型问题：新人进入公司后需要大量时间理解公司、产品、市场和客户；老销售的客户判断和推进经验难以转化为公司的可复用资产。
- **Target Users**: 外贸业务员、销售主管、老板/管理者。

## Goals
- 可读取并分析任意公司导航/产品资料 PDF
- 可从 PDF 中提取结构化公司画像
- 可基于公司画像自动推导目标客户方向
- 可获取一批候选客户样本
- 可对候选客户进行分级并解释原因
- 可根据等级生成下一步动作建议
- 可将结果真实写入飞书多维表
- 可在单页界面中展示多 Agent 协同流程

## Non-Goals (Out of Scope)
- 7 维全量客户挖掘
- 海关数据深挖
- 竞品客户渗透
- 多市场并发切换
- 自动外发邮件 / WhatsApp
- 报价计算
- 权限体系 / 审核流 / CRM 全功能

## Background & Context
- 当前外贸销售场景存在两个典型问题：新人进入公司后需要大量时间理解公司、产品、市场和客户；老销售的客户判断和推进经验沉淀在人脑中，难以转化为公司的可复用资产。
- 现有两份输入材料提供了业务基础：公司导航 PDF（提供企业画像、核心卖点、目标市场、客户画像、弱项及避开客户等信息）和获客智能体 Word（提供完整获客系统蓝图）。
- 本 Demo 设计成 "PDF 驱动的外贸获客智能体"，即用户在开始前导入任意公司导航/产品资料 PDF，系统先自动分析公司，再进入后续获客与分级流程。

## Functional Requirements
- **FR-1**: PDF 上传与解析 - 支持上传任意公司导航/产品资料 PDF，并能解析其内容。
- **FR-2**: 公司画像生成 - 从 PDF 中提取结构化公司画像，包括公司名称、类型、产品、商业模式、核心优势、弱项、优先市场、优先客户类型、应避开的客户类型和缺失字段。
- **FR-3**: 目标客户方向推导 - 基于公司画像推导适合的客户类型、优先市场、应避开的客户类型和需要补充的信息。
- **FR-4**: 候选客户获取 - 根据目标客户方向获取一批候选客户样本，包含公司名称、国家、官网、客户类型、联系方式（如有）和来源链接。
- **FR-5**: 客户分级 - 对候选客户进行 A/B/C/D 分级，并输出分级原因、关键依据和待核实项。
- **FR-6**: 下一步动作建议 - 根据客户等级生成可执行的下一步动作建议，包括优先级、执行主体、触达渠道、跟进时机和开场话术。
- **FR-7**: 飞书多维表落地 - 将最终结果真实写入飞书多维表，包含公司名、国家、官网、客户类型、客户等级、总分、分级原因、关键依据、下一步动作、跟进渠道、开场话术、待核实项和来源链接。
- **FR-8**: 多 Agent 可视化页面 - 通过单页界面展示 5 个 Agent 的工作状态与结果，包括公司识别 Agent、客户搜索 Agent、分级 Agent、动作建议 Agent 和飞书联动 Agent。

## Non-Functional Requirements
- **NFR-1**: 通用性 - 系统不得写死单一公司，必须支持上传任意公司 PDF 后重新生成公司画像并驱动后续流程。
- **NFR-2**: 可解释性 - 每个高优先级客户必须带明确分级依据，不能只有总分。
- **NFR-3**: 可扩展性 - 架构需支持未来扩展，包括多市场、多客户画像、7 维搜索、竞品渗透、海关数据和批量客户池。
- **NFR-4**: 可验证性 - 所有客户信息都必须可追溯来源，不能虚构。
- **NFR-5**: 人机协同 - 系统输出仅作为建议，不直接替代人工最终判断。

## Constraints
- **Technical**: 后端使用 Python 或 Node.js，模型调用使用 OpenAI Responses API，文件输入使用 OpenAI File Inputs，结构化输出使用 Structured Outputs，联网搜索使用内置 Web Search / 外部搜索服务，数据落地使用 Feishu Bitable API，前端使用 React 单页应用。
- **Business**: 交付一个最小可运行闭环（MVP），验证核心能力。
- **Dependencies**: OpenAI API Key、飞书应用凭证、飞书多维表 app_token / table_id、至少 1 个真实测试 PDF。

## Assumptions
- OpenAI 的文件输入能力支持将 PDF 作为 input_file 送入模型，并且在支持视觉的模型上同时提取文本和页面图像。
- Structured Outputs 可保证输出遵循 JSON Schema。
- Responses API 支持在同一流程中处理文件输入和工具调用。
- 飞书多维表格支持通过服务端 API 新增记录。

## Acceptance Criteria

### AC-1: PDF 上传与解析
- **Given**: 用户上传任意公司导航/产品资料 PDF
- **When**: 系统接收并解析 PDF
- **Then**: 系统能成功上传并解析 PDF，返回文件 ID 和存储路径
- **Verification**: `programmatic`

### AC-2: 公司画像生成
- **Given**: 系统已解析 PDF
- **When**: 系统提取公司关键信息
- **Then**: 系统生成结构化公司画像，包含所有必要字段，缺失字段标记为"待确认"
- **Verification**: `programmatic`

### AC-3: 目标客户方向推导
- **Given**: 系统已生成公司画像
- **When**: 系统基于公司画像推导目标客户方向
- **Then**: 系统能从任意 PDF 提取至少 1 个优先市场，能给出至少 1 个目标客户方向，能输出"不适合开发的客户类型"
- **Verification**: `programmatic`

### AC-4: 候选客户获取
- **Given**: 系统已推导目标客户方向
- **When**: 系统搜索候选客户
- **Then**: 系统输出 5–10 家候选客户，每家至少有公司名、国家、官网、来源，找不到联系方式时标记为"待核实"
- **Verification**: `programmatic`

### AC-5: 客户分级
- **Given**: 系统已获取候选客户
- **When**: 系统对候选客户进行分级
- **Then**: 每家客户都有 A/B/C/D 等级，都有分级原因，包含分项评分，找不到的信息体现在不确定性字段里
- **Verification**: `programmatic`

### AC-6: 下一步动作建议
- **Given**: 系统已完成客户分级
- **When**: 系统生成下一步动作建议
- **Then**: 每个客户都有动作建议，动作与等级有明显映射关系，不是泛泛而谈的"建议跟进"
- **Verification**: `programmatic`

### AC-7: 飞书多维表落地
- **Given**: 系统已生成动作建议
- **When**: 系统将结果写入飞书多维表
- **Then**: 记录真实写入飞书，前端显示同步成功/失败，字段内容与后端结果一致
- **Verification**: `programmatic`

### AC-8: 多 Agent 可视化页面
- **Given**: 系统已完成所有流程
- **When**: 用户访问前端页面
- **Then**: 单页可演示完整链路，页面不是聊天框，能明显看到各 Agent 输入/输出/状态
- **Verification**: `human-judgment`
